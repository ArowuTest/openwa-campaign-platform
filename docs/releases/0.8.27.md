# Release 0.8.27 — Platform Governance, Runtime Discovery and Operational Control

## Baseline

- Branch: `work/backend-platform-governance`
- Parent checkpoint: `0.8.26`
- Parent commit: `b84d01b88018eac790332b0ab4d00e05915fe009`

## Gateway-pool and runtime governance

- Added maker-checker gateway-pool creation, submission, approval/rejection and guarded retirement.
- Pool retirement fails while non-retired nodes/sessions, non-terminal campaign routes or active capacity reservations remain.
- Added MFA-protected node drain, offline and retirement operations.
- Added exact-body HMAC runtime registration with timestamp window and durable one-time nonce enforcement.
- Runtime evidence includes node/pool identity, boot ID, provider, engine, adapter, gateway, worker and configuration versions, capabilities, state, capacity, session count, queue depth, CPU and memory.
- Runtime registration rejects malformed/trailing JSON, replay, stale node versions and declared-versus-observed identity/capability drift.
- Accepted and rejected runtime reports receive immutable evidence.

## Shared configuration governance

- Added one platform configuration catalogue with canonical JSON value validation and checksums.
- Supports platform, organisation, environment and campaign scopes.
- Lifecycle supports draft, submission, independent decision, effective-dated activation, supersession and retirement.
- Future replacements preserve the current configuration until the exact effective boundary.
- Equal-start or backdated overlap fails closed.
- Rollback creates a new governed version referencing the source version; history is never overwritten.
- Supersession references and events are stored in the correct direction.

## Maintenance and emergency controls

- Added governed read-only, admission-freeze, draining and emergency-stop windows.
- Windows are scoped to platform, provider, gateway pool or sender pool.
- Non-draining modes always block active dispatch; draining may allow already-active dispatch while rejecting new starts/resumes.
- Enforcement occurs inside API write admission, campaign start/resume, final provider submission and sender-session lifecycle services.
- Expired windows cannot be approved, and ending a future approved window records cancellation rather than an invalid elapsed interval.

## Retention automation

- Added effective-dated, maker-checker retention policies by object type and platform/organisation scope.
- Organisation-specific policies take precedence over platform defaults.
- Added durable retention jobs with claim leases, fencing versions, explicit retry availability, bounded attempts and immutable evidence.
- Stale workers cannot complete, fail or hold reclaimed jobs.
- Supported executors cover inbound-content redaction, import-source deletion and expired-export deletion.
- Active privacy legal holds block conflicting work.
- Incidents, privacy cases and unsupported high-risk/destructive actions are held for review instead of being silently deleted.

## Operational alerts and incidents

- Added governed alert policies for queue depth, unknown outcomes, stale/unavailable nodes, unhealthy sessions, incidents, campaign SLA risk, capacity shortfall and reconciliation backlog.
- Policies support consecutive observations, cooldown, effective dating, supersession, severity, escalation steps and optional automatic incidents.
- Alerts deduplicate, refresh, acknowledge and resolve after recovery.
- Escalation uses fenced leases and stops after acknowledgement.
- Portal notifications are authoritative inbox records and are stored as delivered with delivery evidence.
- Automatic incidents and alert linkage are transactional in PostgreSQL.
- Manual incident creation and updates write timeline events atomically with state.
- Assignment, acknowledgement, investigation, mitigation, resolution and closure are immutable timeline events.
- Terminal incidents cannot silently reopen and terminal outcomes require a resolution.

## Governance worker and deployment

- Added `platform-governance-worker` for retention scheduling/execution, alert evaluation and escalation.
- The worker has bounded cycles, fenced work, health/readiness endpoints and graceful shutdown.
- Added Docker and Compose configuration and separate production settings for runtime-registration signing and governance worker cadence.
