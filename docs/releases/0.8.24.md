# Release 0.8.24 — Backend Hardening, Exact Provider Evidence and Scalable Diagnostics

## Baseline

- Branch: `work/backend-hardening-scalability`
- Parent checkpoint: `0.8.23`
- Parent commit: `c19e8dd529e932e75ada6da694bcd7ad5685eabe`

## Correctness and persistence hardening

- Corrected the PostgreSQL campaign `INSERT` statement so the column list contains valid identifiers rather than expressions.
- Campaign persistence now stores and reads the exact provider capability definition ID and version.
- Critical persisted JSON is decoded fail-closed instead of silently becoming empty state.
- Critical optimistic updates now propagate `RowsAffected` driver errors instead of treating them as success or ordinary conflicts.
- Admission/event evidence and governed opt-out policy persistence now propagate JSON encoding failures.
- Development bootstrap fails closed if the administrator, provider definitions or gateway pools cannot be created.
- Control-plane readiness requires the `0059` provider-binding columns and active-period exclusion constraint.

## Provider and gateway governance

- Added a fail-closed semantic-version comparator for adapter/minimum-gateway compatibility.
- Campaign creation binds the active provider definition selected by provider, channel and engine.
- Final approval, dispatch start, resume and material amendments revalidate the exact binding.
- Provider-definition replacement truncates the superseded effective period and records immutable supersession evidence.
- PostgreSQL route-level advisory locking and an active-period exclusion constraint protect concurrent activation.
- Runtime dispatch validates the frozen campaign definition version, gateway pool, session, provider, engine, adapter, minimum gateway version and required capabilities immediately before submission.

## Controlled test-send hardening

- Test sends freeze the provider adapter, exact provider definition ID and definition version.
- Scheduling validates the message-type capability against the selected governed route.
- Idempotent replay compares the complete frozen request and rejects changed route evidence.
- The campaign worker revalidates the same exact route evidence immediately before a test send.
- Retired definitions, version drift, capability loss or gateway mismatch fail closed.

## Scalability and diagnostics

- Campaign-recipient and transactional-outbox diagnostic reads now use bounded keyset pagination.
- Routing-plan creation now persists campaign-scoped idempotency keys and request hashes; equivalent replays return the original plan and changed-payload replays fail closed.
- Those evidence APIs return database and scan errors explicitly rather than converting failures into empty results.
- Optional UUID cursor/filter queries use `NULLIF` before casting, so an empty cursor cannot fail a PostgreSQL request.
- Operations dashboard totals use `campaign_metrics` for primary state counts rather than repeatedly grouping the complete recipient ledger.
- Sender, gateway, message-version, organisation-policy, opt-out-policy, test-recipient and test-send administrative reads are bounded.
- Added keyset-supporting indexes for campaign recipients, outbox evidence and test-message administration.

## Multi-pool capacity correctness

- Admission now evaluates message-per-minute, hourly and daily limits across the actual campaign execution window.
- Multi-day campaigns can consume a governed daily allowance across successive daily windows instead of being incorrectly rejected against one day.
- Short campaigns fail closed when the hourly allowance cannot satisfy the obligation before the deadline.
- Capacity is resolved against the exact approved sender-pool and gateway-pool route, including healthy-session and minimum-healthy-node evidence.
- Overlapping routing reservations now enforce messages-per-minute, hourly and daily pool ceilings atomically.
- Weighted shard allocation and route-specific execution evidence were corrected for approved multi-pool plans.

## Migration


The migration adds exact provider bindings, effective-period protection and query-supporting indexes. It requires PostgreSQL support for the `btree_gist` extension and must be executed in a production-like PostgreSQL environment before deployment certification.

## Verification boundary
